1. CONTROLLED TESTING WITH MAX RECORDS LIMIT (PRIMARY MODE)
   ─────────────────────────────────────────────────────────────────────────

   For testing purposes, you can configure the file producer to send exactly N
   records and then stop automatically. This is useful for:
   - Load testing with specific record counts (10K, 100K, 1M)
   - Reproducible test scenarios
   - Controlled data volume testing
   - Avoiding infinite data generation during experiments

   PARAMETER: --producer.max.records=<N>
   - Default: -1 (unlimited, producer runs forever until killed)
   - Set to positive number to stop after N records

   EXAMPLES:

   Send exactly 10,000 records then stop:
   cd /home/avoutas/boutasThesis
   java -jar etl-file-producer-1.0.0.jar \
       --kafka.bootstrap.servers=clu02.softnet.tuc.gr:6667,clu03.softnet.tuc.gr:6667,clu04.softnet.tuc.gr:6667,clu06.softnet.tuc.gr:6667 \
       --kafka.input.topic=etl.input.v1 \
       --producer.mode=random \
       --producer.rate.per.sec=240 \
       --producer.max.records=10000

   Send exactly 100,000 records then stop:
   java -jar etl-file-producer-1.0.0.jar \
       --kafka.bootstrap.servers=clu02.softnet.tuc.gr:6667,clu03.softnet.tuc.gr:6667,clu04.softnet.tuc.gr:6667,clu06.softnet.tuc.gr:6667 \
       --kafka.input.topic=etl.input.v1 \
       --producer.mode=random \
       --producer.rate.per.sec=500 \
       --producer.max.records=100000

   Send exactly 1 million records then stop:
   java -jar etl-file-producer-1.0.0.jar \
       --kafka.bootstrap.servers=clu02.softnet.tuc.gr:6667,clu03.softnet.tuc.gr:6667,clu04.softnet.tuc.gr:6667,clu06.softnet.tuc.gr:6667 \

       --producer.mode=random \
       --producer.rate.per.sec=1000 \
       --producer.max.records=1000000

   EXPECTED LOG OUTPUT:
   When limit is reached, you'll see:

   INFO: Reached max records limit: 10000. Stopping producer.
   INFO: ✅ File production COMPLETED. Sent exactly 10000 records (max limit reached).

   The producer process will exit automatically - no need to kill it manually.

   FILE MODE:

- End-to-end processing time: last_record_time - first_record_time
- Throughput: total_records / processing_time_seconds

Look for last "processedAt" timestamp:
Save as: LAST_TIME

STEP 6: Calculate processing time
Convert ISO-8601 timestamps to epoch seconds and subtract:

Example calculation:
FIRST_TIME: 2025-10-12T18:44:21.123Z  → 1728757461 seconds
LAST_TIME:  2025-10-12T18:44:35.456Z  → 1728757475 seconds
Processing time: 1728757475 - 1728757461 = 14 seconds

Throughput: 10,000 records / 14 seconds = 714 records/sec

METHOD 2: Automated Script (Recommended)
────────────────────────────────────────────────────────────────────────────

Create a script to automate timestamp extraction and calculation:

cd /home/avoutas/boutasThesis
cat > measure_throughput.sh << 'EOF'
#!/bin/bash

TOPIC="etl.output.v1"
KAFKA_DIR="/usr/hdp/current/kafka-broker"
BOOTSTRAP_SERVER="clu02.softnet.tuc.gr:6667"

echo "Consuming all messages from $TOPIC..."
$KAFKA_DIR/bin/kafka-console-consumer.sh \
    --bootstrap-server $BOOTSTRAP_SERVER \
    --topic $TOPIC \
    --from-beginning \
    --timeout-ms 5000 > /tmp/output_records.json 2>/dev/null

# Extract all processedAt timestamps (skip config confirmations)
grep -o '"processedAt":"[^"]*"' /tmp/output_records.json | \
    grep -o '[0-9T:.-]*Z' > /tmp/timestamps.txt

FIRST_TS=$(head -1 /tmp/timestamps.txt)
LAST_TS=$(tail -1 /tmp/timestamps.txt)
TOTAL_RECORDS=$(wc -l < /tmp/timestamps.txt)

echo "========================================"
echo "PROCESSING TIME ANALYSIS"
echo "========================================"
echo "First record timestamp: $FIRST_TS"
echo "Last record timestamp:  $LAST_TS"
echo "Total records processed: $TOTAL_RECORDS"

# Convert to epoch seconds (requires date command)
FIRST_EPOCH=$(date -d "$FIRST_TS" +%s 2>/dev/null || echo "0")
LAST_EPOCH=$(date -d "$LAST_TS" +%s 2>/dev/null || echo "0")

if [ "$FIRST_EPOCH" != "0" ] && [ "$LAST_EPOCH" != "0" ]; then
    DURATION=$((LAST_EPOCH - FIRST_EPOCH))
    if [ $DURATION -gt 0 ]; then
        THROUGHPUT=$((TOTAL_RECORDS / DURATION))
        echo "Processing duration:     $DURATION seconds"
        echo "Throughput:              $THROUGHPUT records/sec"
    else
        echo "Duration too short to measure accurately"
    fi
else
    echo "Manual calculation needed (timestamps above)"
fi

echo "========================================"
rm -f /tmp/output_records.json /tmp/timestamps.txt
EOF

chmod +x measure_throughput.sh

────────────────────────────────────────────────────────────────────────────
IMPORTANT NOTES
────────────────────────────────────────────────────────────────────────────

1. WAIT FOR WINDOWS TO FLUSH
   Aggregation windows are 3 seconds by default. After producer finishes,
   wait 5-10 seconds before measuring to ensure all windows have fired.

2. SKIP CONFIG CONFIRMATION MESSAGES
   First message in output topic is config confirmation, NOT data.
   Start timestamp measurement from first aggregation result.

3. CONSIDER KAFKA LAG
   Use output topic timestamps (processedAt), NOT input topic timestamps.
   This captures true Flink processing time.

4. REPEAT TESTS
   Run each test 2-3 times and average results for accuracy.
   First run may be slower due to JVM warmup.

5. MONITOR BACKPRESSURE
   Check Flink dashboard during tests - backpressure indicates bottleneck.
   If you see backpressure, parallelism won't help much.
