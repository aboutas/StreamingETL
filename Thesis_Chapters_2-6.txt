2. ΕΠΙΣΚΟΠΗΣΗ ΣΧΕΤΙΚΗΣ ΕΡΕΥΝΑΣ

Το παρόν κεφάλαιο παρουσιάζει μια συνολική επισκόπηση των τεχνολογιών και των
ερευνητικών προσεγγίσεων που σχετίζονται με την επεξεργασία ροών δεδομένων σε
πραγματικό χρόνο και τα συστήματα ETL (Extract, Transform, Load).

2.1 Πλατφόρμες Επεξεργασίας Ροών Δεδομένων

Η επεξεργασία ροών δεδομένων (stream processing) έχει εξελιχθεί σημαντικά τα
τελευταία χρόνια, με την ανάπτυξη εξειδικευμένων πλατφορμών που επιτρέπουν την
επεξεργασία μεγάλων όγκων δεδομένων σε πραγματικό χρόνο.

2.1.1 Apache Flink

Το Apache Flink αποτελεί μια κατανεμημένη μηχανή επεξεργασίας ροών και ομαδικής
επεξεργασίας (batch processing) που έχει σχεδιαστεί για να παρέχει υψηλή απόδοση,
ανοχή σε σφάλματα και ακρίβεια στην επεξεργασία δεδομένων. Τα κύρια χαρακτηριστικά
του περιλαμβάνουν:

- Πραγματική επεξεργασία ροών (true streaming): Το Flink επεξεργάζεται τα δεδομένα
  ως συνεχείς ροές, όχι ως μικρά ομαδικά σύνολα (micro-batches).

- Εγγυήσεις ακριβούς μίας επεξεργασίας (exactly-once semantics): Μέσω του
  μηχανισμού checkpointing, το Flink εξασφαλίζει ότι κάθε γεγονός επεξεργάζεται
  ακριβώς μία φορά, ακόμη και σε περίπτωση αποτυχίας.

- Χαμηλή καθυστέρηση (low latency): Το Flink παρέχει χαμηλή καθυστέρηση στην
  επεξεργασία δεδομένων, καθιστώντας το ιδανικό για εφαρμογές πραγματικού χρόνου.

- Πλούσιο API: Το DataStream API του Flink προσφέρει εκτενείς δυνατότητες για
  μετασχηματισμούς, συναθροίσεις, παράθυρα και κατάσταση.

- Κλιμακωσιμότητα: Το Flink μπορεί να κλιμακωθεί οριζόντια σε εκατοντάδες κόμβους.

2.1.2 Άλλες Πλατφόρμες Επεξεργασίας Ροών

- Apache Storm: Μια από τις πρώτες πλατφόρμες επεξεργασίας ροών, προσφέρει
  επεξεργασία σε πραγματικό χρόνο αλλά με εγγυήσεις τουλάχιστον μίας επεξεργασίας
  (at-least-once semantics).

- Apache Spark Streaming: Χρησιμοποιεί προσέγγιση micro-batching, όπου οι ροές
  χωρίζονται σε μικρά ομαδικά σύνολα που επεξεργάζονται σε διαστήματα δευτερολέπτων.

- Apache Kafka Streams: Μια ελαφριά βιβλιοθήκη για επεξεργασία ροών που ενσωματώνεται
  άμεσα με το Kafka, κατάλληλη για απλές μετασχηματιστικές εργασίες.

Σύγκριση με το Flink:
Το Flink ξεχωρίζει με την πραγματική επεξεργασία ροών του και τις εγγυήσεις
exactly-once, καθώς και με τη χαμηλή καθυστέρηση που προσφέρει. Για αυτούς τους
λόγους, επιλέχθηκε ως η κύρια πλατφόρμα επεξεργασίας στο παρόν σύστημα.


2.2 Συστήματα Ουρών Μηνυμάτων

Τα συστήματα ουρών μηνυμάτων (message queue systems) αποτελούν βασικό στοιχείο
των κατανεμημένων αρχιτεκτονικών, επιτρέποντας την ασύγχρονη επικοινωνία μεταξύ
διαφορετικών υπηρεσιών.

2.2.1 Αρχιτεκτονική Apache Kafka

Το Apache Kafka είναι μια κατανεμημένη πλατφόρμα ροής γεγονότων (distributed
event streaming platform) που χρησιμοποιείται ευρέως για την κατασκευή αγωγών
δεδομένων σε πραγματικό χρόνο. Η αρχιτεκτονική του περιλαμβάνει:

Βασικά Στοιχεία:

- Topics (Θέματα): Κατηγορίες στις οποίες αποθηκεύονται οι εγγραφές. Κάθε topic
  οργανώνεται ως ένα κατανεμημένο log.

- Partitions (Διαμερίσματα): Κάθε topic χωρίζεται σε ένα ή περισσότερα partitions
  για κλιμάκωση και παραλληλισμό. Κάθε partition είναι ένα ταξινομημένο, αμετάβλητο
  αλληλουχία εγγραφών.

- Brokers (Μεσίτες): Οι κόμβοι του Kafka cluster που αποθηκεύουν τα δεδομένα και
  εξυπηρετούν τους παραγωγούς και καταναλωτές.

- Producers (Παραγωγοί): Εφαρμογές που δημοσιεύουν μηνύματα σε topics.

- Consumers (Καταναλωτές): Εφαρμογές που εγγράφονται σε topics και επεξεργάζονται
  τις εγγραφές.

- Consumer Groups (Ομάδες Καταναλωτών): Επιτρέπουν την κατανομή της επεξεργασίας
  μεταξύ πολλαπλών καταναλωτών.

- Zookeeper: Διαχειρίζεται τη διαμόρφωση και τον συντονισμό του Kafka cluster
  (σε παλαιότερες εκδόσεις).

Πλεονεκτήματα του Kafka:

- Υψηλή διεκπεραιωτικότητα (high throughput): Δυνατότητα χειρισμού εκατομμυρίων
  μηνυμάτων ανά δευτερόλεπτο.

- Χαμηλή καθυστέρηση: Χρόνος απόκρισης της τάξης των χιλιοστών του δευτερολέπτου.

- Ανθεκτικότητα (durability): Τα δεδομένα αποθηκεύονται στον δίσκο και αντιγράφονται
  μεταξύ πολλαπλών brokers.

- Κλιμακωσιμότητα: Δυνατότητα οριζόντιας κλιμάκωσης με την προσθήκη περισσότερων
  brokers και partitions.

2.2.2 Άλλα Συστήματα Ουρών

- RabbitMQ: Παραδοσιακό message broker που υλοποιεί το AMQP πρωτόκολλο, κατάλληλο
  για σύνθετα μοτίβα routing.

- Apache Pulsar: Νεότερη πλατφόρμα με υποστήριξη multi-tenancy και geo-replication.

- Amazon Kinesis: Διαχειριζόμενη υπηρεσία streaming στο AWS.


2.3 Συστήματα και Προσεγγίσεις ETL

Η διαδικασία ETL (Extract, Transform, Load) αποτελεί θεμελιώδη μέθοδο για τη
μεταφορά και μετασχηματισμό δεδομένων μεταξύ συστημάτων.

2.3.1 Παραδοσιακά Συστήματα ETL (Batch ETL)

Τα παραδοσιακά συστήματα ETL λειτουργούν σε ομαδική επεξεργασία (batch mode),
επεξεργαζόμενα μεγάλα σύνολα δεδομένων σε προγραμματισμένα διαστήματα:

Χαρακτηριστικά:

- Ομαδική επεξεργασία: Τα δεδομένα συλλέγονται και επεξεργάζονται σε τακτά
  διαστήματα (π.χ. ανά ώρα, ημερησίως).

- Υψηλή καθυστέρηση: Από λεπτά έως ώρες μεταξύ της συλλογής και της διαθεσιμότητας
  των δεδομένων.

- Σύνθετοι μετασχηματισμοί: Δυνατότητα εκτέλεσης πολύπλοκων αναλύσεων και
  μετασχηματισμών.

Εργαλεία:

- Apache Hadoop με MapReduce
- Apache Spark (batch mode)
- Παραδοσιακά ETL εργαλεία (Informatica, Talend, Pentaho)

Περιορισμοί:

- Αδυναμία επεξεργασίας σε πραγματικό χρόνο
- Υψηλή αδράνεια στη λήψη αποφάσεων
- Περιορισμένη ευελιξία στη διαχείριση δυναμικών αλλαγών

2.3.2 ETL σε Πραγματικό Χρόνο (Streaming ETL)

Τα σύγχρονα συστήματα streaming ETL επεξεργάζονται τα δεδομένα καθώς παράγονται,
προσφέροντας σημαντικά πλεονεκτήματα:

Χαρακτηριστικά:

- Συνεχής επεξεργασία: Τα δεδομένα επεξεργάζονται αμέσως μόλις λαμβάνονται.

- Χαμηλή καθυστέρηση: Από χιλιοστά έως δευτερόλεπτα.

- Δυναμική διαμόρφωση: Δυνατότητα αλλαγής των κανόνων μετασχηματισμού χωρίς
  διακοπή της υπηρεσίας.

- Αντίδραση σε γεγονότα: Άμεση απόκριση σε κρίσιμα γεγονότα.

Προσεγγίσεις:

- Lambda Architecture: Συνδυασμός batch και streaming επεξεργασίας για εξισορρόπηση
  μεταξύ ακρίβειας και καθυστέρησης.

- Kappa Architecture: Αμιγής προσέγγιση streaming που απλοποιεί την αρχιτεκτονική
  χρησιμοποιώντας μόνο επεξεργασία ροών.

Σύγχρονα Εργαλεία:

- Apache Flink για streaming ETL
- Apache Kafka για data pipelines
- Apache Beam για ενοποιημένο μοντέλο προγραμματισμού

Σύγκριση:

Το παρόν σύστημα υιοθετεί την προσέγγιση Kappa Architecture με χρήση Apache Flink
και Kafka, προσφέροντας πραγματική επεξεργασία σε πραγματικό χρόνο με δυναμική
διαμόρφωση μετασχηματισμών.


2.4 Σχετικές Έρευνες και Εφαρμογές

Πρόσφατες έρευνες έχουν επικεντρωθεί στη βελτιστοποίηση της επεξεργασίας ροών
και την ανάπτυξη ευέλικτων αρχιτεκτονικών:

- Δυναμική ανάθεση πόρων: Αλγόριθμοι για την αυτόματη κλιμάκωση των πόρων με βάση
  το φορτίο.

- Προσαρμοστική επεξεργασία: Συστήματα που προσαρμόζουν τη στρατηγική επεξεργασίας
  με βάση τα χαρακτηριστικά των δεδομένων.

- Internet of Things (IoT): Επεξεργασία ροών από αισθητήρες σε πραγματικό χρόνο.

- Ανίχνευση ανωμαλιών: Εντοπισμός ασυνήθιστων μοτίβων σε ροές δεδομένων.

3. ΘΕΩΡΗΤΙΚΟ ΥΠΟΒΑΘΡΟ

Το κεφάλαιο αυτό παρουσιάζει τις θεμελιώδεις έννοιες και τεχνολογίες που απαιτούνται
για την κατανόηση του συστήματος ETL που υλοποιήθηκε.

3.1 Θεμελιώδεις Έννοιες Επεξεργασίας Ροών

3.1.1 Επεξεργασία Ροών έναντι Batch Επεξεργασίας

Η επεξεργασία ροών (stream processing) και η ομαδική επεξεργασία (batch processing)
αποτελούν δύο διαφορετικές παραδείγματα επεξεργασίας δεδομένων:

Batch Processing:
- Τα δεδομένα είναι πεπερασμένα και στατικά
- Επεξεργασία ολόκληρου του συνόλου δεδομένων ταυτόχρονα
- Υψηλή καθυστέρηση (ώρες έως ημέρες)
- Κατάλληλο για ιστορικές αναλύσεις και αναφορές
- Παραδείγματα: Nightly reports, data warehousing

Stream Processing:
- Τα δεδομένα είναι δυνητικά άπειρα και συνεχώς ενημερώνονται
- Επεξεργασία κάθε γεγονότος ή μικρών ομάδων γεγονότων καθώς φτάνουν
- Χαμηλή καθυστέρηση (χιλιοστά έως δευτερόλεπτα)
- Κατάλληλο για real-time analytics και άμεσες αντιδράσεις
- Παραδείγματα: Fraud detection, real-time monitoring

3.1.2 Μοντέλο Επεξεργασίας Ροών

Βασικά στοιχεία:

- Γεγονότα (Events): Μεμονωμένες εγγραφές δεδομένων που ρέουν στο σύστημα

- Ροές (Streams): Συνεχείς ακολουθίες γεγονότων ταξινομημένες χρονικά

- Μετασχηματισμοί (Transformations): Λειτουργίες που εφαρμόζονται στα γεγονότα
  (map, filter, flatMap, κ.ά.)

- Χρόνος (Time): Τρία είδη χρόνου:
  * Event time: Πότε δημιουργήθηκε το γεγονός
  * Ingestion time: Πότε εισήλθε στο σύστημα
  * Processing time: Πότε επεξεργάστηκε

- Κατάσταση (State): Πληροφορίες που διατηρούνται μεταξύ γεγονότων

3.1.3 Εγγυήσεις Επεξεργασίας

- At-most-once: Κάθε γεγονός επεξεργάζεται το πολύ μία φορά (δυνατότητα απώλειας)

- At-least-once: Κάθε γεγονός επεξεργάζεται τουλάχιστον μία φορά (δυνατότητα
  διπλότυπων)

- Exactly-once: Κάθε γεγονός επεξεργάζεται ακριβώς μία φορά (ιδανικό σενάριο)

Το Apache Flink υποστηρίζει exactly-once semantics μέσω του μηχανισμού checkpointing.


3.2 Βασικές Έννοιες Apache Flink

3.2.1 DataStream API

Το DataStream API αποτελεί το κύριο API για την ανάπτυξη εφαρμογών επεξεργασίας
ροών στο Flink. Βασικά στοιχεία:

Sources (Πηγές):
- Σημεία εισόδου δεδομένων στο Flink
- Παραδείγματα: Kafka, files, sockets
- Στο σύστημά μας: FlinkKafkaConsumer

Transformations (Μετασχηματισμοί):
- map(): Μετασχηματισμός 1-προς-1
- filter(): Φιλτράρισμα γεγονότων
- flatMap(): Μετασχηματισμός 1-προς-πολλά
- keyBy(): Ομαδοποίηση με βάση κλειδί
- connect(): Σύνδεση δύο ροών

Sinks (Καταβόθρες):
- Σημεία εξόδου δεδομένων από το Flink
- Παραδείγματα: Kafka, databases, files
- Στο σύστημά μας: FlinkKafkaProducer

3.2.2 CoFlatMap: Επεξεργασία Συνδεδεμένων Ροών

Το CoFlatMap επιτρέπει την επεξεργασία δύο συνδεδεμένων ροών με κοινή κατάσταση:

```java
public abstract class CoFlatMapFunction<IN1, IN2, OUT> {
    // Επεξεργασία πρώτης ροής (configurations)
    public abstract void flatMap1(IN1 value, Collector<OUT> out);

    // Επεξεργασία δεύτερης ροής (data events)
    public abstract void flatMap2(IN2 value, Collector<OUT> out);
}
```

Στο σύστημά μας:
- Ροή 1 (flatMap1): Configurations ETL - αποθηκεύονται σε κατάσταση
- Ροή 2 (flatMap2): Sensor events - επεξεργάζονται με βάση τις configurations

Πλεονεκτήματα:
- Δυναμική ενημέρωση κανόνων χωρίς restart
- Διατήρηση κατάστασης ανά key group
- Πραγματικός παραλληλισμός με keyBy

3.2.3 Κατάσταση και Διαχείριση Κατάστασης

Το Flink προσφέρει πλούσια API για τη διαχείριση κατάστασης:

ValueState<T>: Αποθήκευση μεμονωμένης τιμής
ListState<T>: Αποθήκευση λίστας τιμών
MapState<K,V>: Αποθήκευση ζευγών κλειδί-τιμή

Στο σύστημά μας:
```java
MapState<String, EtlConfig> configState;
```

Checkpointing:
- Περιοδική αποθήκευση της κατάστασης
- Επιτρέπει ανάκτηση από αποτυχίες
- Εγγυάται exactly-once semantics

3.2.4 Παράθυρα (Windows)

Τα παράθυρα ομαδοποιούν γεγονότα για συναθροιστική επεξεργασία:

Tumbling Windows (Διαδοχικά Παράθυρα):
- Σταθερού μεγέθους, χωρίς επικάλυψη
- Παράδειγμα: Παράθυρα 3 δευτερολέπτων
- Χρήση: TumblingProcessingTimeWindows.of(Time.seconds(3))

Sliding Windows (Ολισθαίνοντα Παράθυρα):
- Σταθερού μεγέθους με επικάλυψη
- Παράδειγμα: Παράθυρα 10 δευτερολέπτων κάθε 5 δευτερόλεπτα

Session Windows (Παράθυρα Συνεδρίας):
- Δυναμικού μεγέθους με βάση την αδράνεια
- Κλείνουν μετά από timeout χωρίς δραστηριότητα

Στο σύστημά μας χρησιμοποιούμε Tumbling Windows 3 δευτερολέπτων για τις
συναθροίσεις.

3.2.5 Event Time και Watermarks

Event Time: Ο χρόνος που δημιουργήθηκε το γεγονός (πιο ακριβής)
Processing Time: Ο χρόνος επεξεργασίας (πιο απλός)

Watermarks:
- Σήματα που υποδεικνύουν την πρόοδο του event time
- Επιτρέπουν το κλείσιμο παραθύρων ακόμη και με καθυστερημένα γεγονότα
- BoundedOutOfOrdernessTimestampExtractor: Χειρίζεται out-of-order events


3.3 Θεμελιώδεις Έννοιες Apache Kafka

3.3.1 Topics και Partitions

Topics:
- Λογικές κατηγορίες για την οργάνωση μηνυμάτων
- Κάθε μήνυμα ανήκει σε ένα topic
- Στο σύστημά μας: etl.config.v1, etl.input.v1, etl.output.v1

Partitions:
- Φυσικός διαμερισμός ενός topic
- Επιτρέπει παραλληλισμό και κλιμάκωση
- Κάθε partition είναι ordered log
- Μηνύματα με το ίδιο key πηγαίνουν στο ίδιο partition

Παράδειγμα:
```
Topic: etl.input.v1
├── Partition 0: [msg1, msg3, msg5, ...]
├── Partition 1: [msg2, msg6, msg10, ...]
├── Partition 2: [msg4, msg7, msg11, ...]
└── Partition 3: [msg8, msg9, msg12, ...]
```

Replication:
- Κάθε partition αντιγράφεται σε πολλαπλούς brokers
- Replication factor: αριθμός αντιγράφων
- Leader-follower μοντέλο για υψηλή διαθεσιμότητα

3.3.2 Producers και Consumers

Producers (Παραγωγοί):
- Δημοσιεύουν μηνύματα σε topics
- Επιλέγουν partition (με key ή round-robin)
- Μπορούν να περιμένουν επιβεβαίωση (acks)

Στο σύστημά μας:
- ETL API: Παραγωγός configurations στο etl.config.v1
- File Producer: Παραγωγός sensor data στο etl.input.v1
- Flink Job: Παραγωγός results στο etl.output.v1

Consumers (Καταναλωτές):
- Διαβάζουν μηνύματα από topics
- Κρατούν offset: θέση στο log
- Μπορούν να ξεκινήσουν από earliest, latest, ή συγκεκριμένο offset

Consumer Groups:
- Ομάδα καταναλωτών που μοιράζονται τη φόρτο εργασίας
- Κάθε partition αντιστοιχεί σε έναν καταναλωτή στην ομάδα
- Επιτρέπει παράλληλη επεξεργασία

Στο σύστημά μας:
- Flink Job: Καταναλωτής με group.id = "etl-flink-consumer"

3.3.3 Εγγυήσεις Παράδοσης

Kafka προσφέρει διάφορες εγγυήσεις:

At-most-once: acks=0 (χωρίς επιβεβαίωση)
At-least-once: acks=1 (επιβεβαίωση από leader)
Exactly-once: acks=all + idempotent producer + transactions

Στο Flink Kafka Connector:
- FlinkKafkaProducer.Semantic.AT_LEAST_ONCE
- FlinkKafkaProducer.Semantic.EXACTLY_ONCE (με Kafka transactions)

3.4 Μετασχηματισμοί ETL

3.4.1 Φιλτράρισμα Δεδομένων

Το φιλτράρισμα αποτελεί θεμελιώδη λειτουργία ETL που επιλέγει συγκεκριμένα
γεγονότα με βάση κριτήρια:

Filter Greater (filter_greater):
- Διατηρεί γεγονότα όπου ένα πεδίο είναι μεγαλύτερο από όριο
- Παράδειγμα: measurement > 25.0 (θερμοκρασίες πάνω από 25°C)

Filter Less (filter_less):
- Διατηρεί γεγονότα όπου ένα πεδίο είναι μικρότερο από όριο
- Παράδειγμα: measurement < 0.0 (αρνητικές θερμοκρασίες)

Filter Cross-Field (filter_cross_field):
- Συγκρίνει δύο πεδία του ίδιου γεγονότος
- Παράδειγμα: temperature > humidity

Sensor Filtering:
- Φιλτράρισμα με βάση τον τύπο αισθητήρα
- Επιτρέπει διαφορετικές επεξεργασίες ανά sensor type

Υλοποίηση:
```java
public class FilterGreaterTransformation implements MapFunction<SensorEvent, SensorEvent> {
    private String field;
    private double threshold;

    public SensorEvent map(SensorEvent event) {
        double value = event.getMeasurement();
        return value > threshold ? event : null;
    }
}
```

3.4.2 Συναθροίσεις (Aggregations)

Οι συναθροίσεις υπολογίζουν συγκεντρωτικά μετρικά από ομάδες γεγονότων:

Sum (Άθροισμα):
- Υπολογίζει το άθροισμα των τιμών
- Χρήση: Συνολική κατανάλωση ενέργειας, συνολική βροχόπτωση

Average (Μέσος Όρος):
- Υπολογίζει τον μέσο όρο των τιμών
- Χρήση: Μέση θερμοκρασία, μέση υγρασία

Maximum (Μέγιστο):
- Βρίσκει τη μέγιστη τιμή
- Χρήση: Μέγιστη θερμοκρασία ημέρας

Minimum (Ελάχιστο):
- Βρίσκει την ελάχιστη τιμή
- Χρήση: Ελάχιστη θερμοκρασία νύχτας

Υλοποίηση με AggregateFunction:
```java
public interface AggregateFunction<IN, ACC, OUT> {
    ACC createAccumulator();
    ACC add(IN value, ACC accumulator);
    OUT getResult(ACC accumulator);
    ACC merge(ACC a, ACC b);
}
```

3.4.3 Συναθροίσεις με Παράθυρα

Οι συναθροίσεις συνδυάζονται με παράθυρα για χρονικά περιορισμένους υπολογισμούς:

Tumbling Window Aggregation:
- Συναθροίσεις σε σταθερά διαστήματα
- Παράδειγμα: Μέσος όρος ανά 3 δευτερόλεπτα

```java
dataStream
    .keyBy("sensor")
    .window(TumblingProcessingTimeWindows.of(Time.seconds(3)))
    .aggregate(new AverageAggregator())
```

Sliding Window Aggregation:
- Συναθροίσεις με επικαλυπτόμενα παράθυρα
- Χρήση: Κινούμενος μέσος όρος

Session Window Aggregation:
- Συναθροίσεις για sessions με inactivity gap
- Χρήση: Ανάλυση συνεδριών χρήστη

Key-Based Grouping:
- Συναθροίσεις ανά ομάδα (π.χ. ανά sensor, ανά location)
- Παραλληλισμός με βάση το key

Παράδειγμα από το σύστημα:
- Tumbling windows 3 δευτερολέπτων
- Grouping με: jobId | sensor | aggregationType
- WindowAccumulator διατηρεί sum, count, min, max


3.5 Αρχιτεκτονικά Πρότυπα

3.5.1 Lambda Architecture

Συνδυάζει batch και streaming layers:
- Batch layer: Ιστορικά δεδομένα, υψηλή ακρίβεια
- Speed layer: Real-time δεδομένα, χαμηλή καθυστέρηση
- Serving layer: Ενοποιημένη προβολή

Μειονεκτήματα:
- Πολυπλοκότητα: Δύο συστήματα να συντηρηθούν
- Δυσκολία συγχρονισμού

3.5.2 Kappa Architecture

Απλοποιημένη προσέγγιση με μόνο streaming:
- Ενιαίο σύστημα επεξεργασίας
- Reprocessing μέσω replay του log
- Χαμηλότερη πολυπλοκότητα

Το σύστημά μας ακολουθεί Kappa Architecture:
- Apache Flink για όλη την επεξεργασία
- Kafka ως distributed log
- Δυνατότητα replay για reprocessing

4.3 Μετασχηματισμοί και Φιλτράρισμα Ροών

Απαίτηση FR-04: Φιλτράρισμα Γεγονότων

Το σύστημα πρέπει να υποστηρίζει διάφορους τύπους φίλτρων:

Filter Greater:
- Φιλτράρισμα γεγονότων με τιμή > threshold
- Παράμετροι: field, threshold
- Χρήση: Ανίχνευση υψηλών θερμοκρασιών, υπέρβασης ορίων

Filter Less:
- Φιλτράρισμα γεγονότων με τιμή < threshold
- Παράμετροι: field, threshold
- Χρήση: Ανίχνευση χαμηλών τιμών, παγετού

Filter Cross-Field:
- Σύγκριση δύο πεδίων στο ίδιο γεγονός
- Παράμετροι: field1, field2, operator
- Χρήση: Σύγκριση θερμοκρασίας-υγρασίας

Sensor Filter:
- Φιλτράρισμα με βάση τον τύπο αισθητήρα
- Επιτρέπει διαφορετικούς μετασχηματισμούς ανά sensor type

Απαίτηση FR-05: Μετασχηματισμοί Δεδομένων

Υποστήριξη βασικών μετασχηματισμών:
- Normalize: Κανονικοποίηση τιμών σε εύρος [0, 1]
- To Lowercase: Μετατροπή κειμένου σε πεζά
- Trim Whitespace: Αφαίρεση κενών διαστημάτων

Προδιαγραφές:
- Εφαρμογή σε επίπεδο γεγονότος
- Διατήρηση μεταδεδομένων (sensor, location, κ.ά.)
- Καταγραφή εφαρμοσμένων μετασχηματισμών (diagnostics)


4.4 Συναθροίσεις με Παράθυρα

Απαίτηση FR-06: Υποστήριξη Συναθροιστικών Λειτουργιών

Το σύστημα πρέπει να υποστηρίζει τις ακόλουθες συναθροίσεις:

Sum (Άθροισμα):
- Υπολογισμός αθροίσματος τιμών
- Χρήση: Συνολική κατανάλωση, σύνολο γεγονότων

Maximum (Μέγιστο):

Minimum (Ελάχιστο):
- Εύρεση ελάχιστης τιμής

5.1.2 Αρχιτεκτονική Ροής Δεδομένων

Το σύστημα ακολουθεί την αρχιτεκτονική Kappa με τρία κύρια συστατικά:

1. Παραγωγοί (Producers):

   - File Producer: Παραγωγός sensor data

   - Flink Job: Κεντρική μονάδα επεξεργασίας
   - CoFlatMap: Δυναμική εφαρμογή configurations
   - Windowing: Χρονικές συναθροίσεις

3. Καταναλωτές (Consumers):
   - Kafka Output Topic: Αποτελέσματα
   - External Systems: Παρακολούθηση, αποθήκευση

5.1.3 Σχεδιαστικές Αποφάσεις

Απόφαση 1: Χρήση CoFlatMap για Δυναμική Διαμόρφωση

Αιτιολόγηση:
- Επιτρέπει δυναμική ενημέρωση configurations χωρίς restart
- Διατηρεί κατάσταση ανά subtask για πραγματικό παραλληλισμό
- Συνδέει δύο ροές (config + data) με κοινή κατάσταση

Εναλλακτικές:
- BroadcastState: Αντιγράφει configurations σε όλα τα subtasks (overhead)
- External Configuration Store: Αυξάνει latency με εξωτερικά queries

Απόφαση 2: KeyBy με Sensor για Πραγματικό Παραλληλισμό

Αιτιολόγηση:
- Κάθε configuration αποθηκεύεται μόνο στα subtasks που χρειάζονται
- Sensor-based keying διασφαλίζει ότι data και configs συναντώνται
- Βελτιστοποιεί χρήση μνήμης και επεξεργαστή

Υλοποίηση:
```java
// Config stream keying
configStream.keyBy(new ConfigKeyExtractor())

// Data stream keying
eventStream.keyBy(event -> event.getSensor())
```

Απόφαση 3: Tumbling Windows 3 Δευτερολέπτων

Αιτιολόγηση:
- Εξισορροπεί χαμηλή καθυστέρηση και υπολογιστική αποδοτικότητα
- Επαρκής χρόνος για συλλογή αρκετών γεγονότων
- Συμβατό με real-time απαιτήσεις

Εναλλακτικές:
- 1s windows: Πολύ μικρά, ανεπαρκή δεδομένα
- 10s windows: Μεγάλη καθυστέρηση για real-time

Απόφαση 4: Διαχωρισμός σε Τρεις Υπηρεσίες

Αιτιολόγηση:
- Separation of concerns: Κάθε υπηρεσία έχει ξεχωριστό ρόλο

Η κλάση CoFlatMapProcessor υλοποιεί τη δυναμική επεξεργασία:

```java
public class CoFlatMapProcessor
    extends RichCoFlatMapFunction<EtlConfig, SensorEvent, EtlResult> {

    private transient MapState<String, EtlConfig> configState;

    @Override
    public void open(Configuration parameters) {
        // Initialize state
        configState = getRuntimeContext().getMapState(
            new MapStateDescriptor<>("configs-by-key",
                String.class, EtlConfig.class)
        );
    }

    @Override
    public void flatMap1(EtlConfig config, Collector<EtlResult> out) {
        LOG.info("Received config for job: {} on subtask: {}",
            config.getJobId(),
            getRuntimeContext().getIndexOfThisSubtask());

        // Store configuration
        configState.put(config.getJobId(), config);

        // Emit confirmation
        EtlResult confirmation = new EtlResult();
        confirmation.setJobId(config.getJobId());
        confirmation.setResult("Configuration registered successfully");
        confirmation.setProcessedAt(ZonedDateTime.now(GREEK_TIMEZONE)
            .toInstant());

        out.collect(confirmation);
    }

    @Override
    public void flatMap2(SensorEvent event, Collector<EtlResult> out) {
        // Process event against all configs in this subtask
        for (Map.Entry<String, EtlConfig> entry : configState.entries()) {
            EtlConfig config = entry.getValue();

            try {
                processEventWithConfig(event, config, out);
            } catch (Exception e) {
                LOG.error("Error processing event", e);
                emitErrorResult(event, config, e, out);
            }
        }
    }
}
```

Λεπτομέρειες Υλοποίησης:

1. Διαχωρισμός Transformations:
```java
private void processEventWithConfig(SensorEvent event, EtlConfig config,
                                   Collector<EtlResult> out) {
    // Separate element and aggregation transformations
    List<Transformation> elementTransformations = new ArrayList<>();
    List<Transformation> aggregationTransformations = new ArrayList<>();

    for (Transformation t : config.getTransformations()) {
        if (isElementTransformation(t.getType())) {
            elementTransformations.add(t);
        } else if (isAggregationTransformation(t.getType())) {
            aggregationTransformations.add(t);
        }
    }

    // Apply element transformations first
    SensorEvent filteredEvent = event;
    for (Transformation t : elementTransformations) {
        filteredEvent = applyElementTransformation(filteredEvent, t);
        if (filteredEvent == null) break;  // Filtered out
    }

    // Apply aggregation transformations
    for (Transformation t : aggregationTransformations) {
        processWindowedAggregation(event, t, config, out);
    }
}
```

```java
private boolean processWindowedAggregation(SensorEvent event,
                                          Transformation transformation,
                                          EtlConfig config,
                                          Collector<EtlResult> out) {
    String sensorFilter = getSensorFromParams(transformation.getParams());

    // Apply sensor filter if specified
    if (sensorFilter != null &&
        !sensorFilter.equals(event.getSensor())) {
        return false;  // Skip this event
    }

    // Create result for windowing
    EtlResult result = new EtlResult();
    result.setJobId(config.getJobId());
    result.setAggregationType(transformation.getType());
    result.setField(getFieldFromParams(transformation.getParams()));
    result.setResult(getFieldValue(event, field));

    // Add context information
    result.setSensorType(event.getSensor());
    result.setMeasurementUnit(event.getMeasurementUnit());
    result.setLocation(event.getLocation());

    out.collect(result);
    return true;
}
```

```java
public class ConfigKeyExtractor implements KeySelector<EtlConfig, String> {

    @Override
    public String getKey(EtlConfig config) throws Exception {
        // Extract sensor from aggregation transformations
        for (Transformation t : config.getTransformations()) {
            if (isAggregation(t.getType())) {
                String sensor = getSensorFromParams(t.getParams());
                if (sensor != null) {
                    return sensor;  // Key by sensor
                }
            }
        }

        // Fallback: Use jobId as key
        return config.getJobId();
    }

    private String getSensorFromParams(Map<String, Object> params) {
        if (params != null && params.containsKey("sensor")) {
            return (String) params.get("sensor");
        }
        return null;
    }
}
```

- Εξάγει το sensor από τις παραμέτρους των aggregations
- Διασφαλίζει ότι configurations και events με το ίδιο sensor

- Επιτρέπει πραγματικό παραλληλισμό

6.1.5 WindowAggregator

Aggregation function για παράθυρα:

```java
public static class WindowAggregator
    implements AggregateFunction<EtlResult, WindowAccumulator, EtlResult> {

    @Override
    public WindowAccumulator createAccumulator() {
        return new WindowAccumulator();
    }

    @Override
    public WindowAccumulator add(EtlResult result, WindowAccumulator acc) {
        // Initialize accumulator on first add
        if (acc.jobId == null) {
            acc.jobId = result.getJobId();
            acc.aggregationType = result.getAggregationType();
            acc.field = result.getField();
            acc.sensorType = result.getSensorType();
            acc.measurementUnit = result.getMeasurementUnit();
            acc.location = result.getLocation();
        }

        // Accumulate value
        Double value = (Double) result.getResult();
        if (value != null) {
            acc.accumulate(value);
            acc.count++;
        }

        return acc;
    }

    @Override
    public EtlResult getResult(WindowAccumulator acc) {
        EtlResult result = new EtlResult();
        result.setJobId(acc.jobId);
        result.setAggregationType(acc.aggregationType);
        result.setField(acc.field);
        result.setResult(acc.getResult());  // Compute final result
        result.setProcessedAt(ZonedDateTime.now(GREEK_TIMEZONE).toInstant());

        // Add context
        result.setSensorType(acc.sensorType);
        result.setMeasurementUnit(acc.measurementUnit);
        result.setLocation(acc.location);

        // Add diagnostics
        List<String> diagnostics = new ArrayList<>();
        diagnostics.add(String.format("WINDOWED %s: %d values = %.2f",
            acc.aggregationType, acc.count, acc.getResult()));
        diagnostics.add("Window: 3s tumbling window");
        result.setDiagnostics(diagnostics);

        return result;
    }

    @Override
    public WindowAccumulator merge(WindowAccumulator a, WindowAccumulator b) {
        a.sum += b.sum;
        a.count += b.count;
        if (b.max > a.max) a.max = b.max;
        if (b.min < a.min) a.min = b.min;
        return a;
    }
}
```

WindowAccumulator:
```java
public static class WindowAccumulator {
    public String jobId;
    public String aggregationType;
    public String field;
    public String sensorType;
    public String measurementUnit;
    public String location;
    public int count = 0;

    public Double sum = 0.0;
    public Double max = Double.NEGATIVE_INFINITY;
    public Double min = Double.POSITIVE_INFINITY;

    public void accumulate(Double value) {
        sum += value;
        if (value > max) max = value;
        if (value < min) min = value;
    }

    public Double getResult() {
        switch (aggregationType) {
            case "sum": return sum;
            case "avg": return count > 0 ? sum / count : 0.0;
            case "max": return max;
            case "min": return min;
            default: return sum;
        }
    }
}
```

```java
            LOG.warn("Validation failed: {}", e.getMessage());
            response.put("status", "error");
            response.put("message", "Validation error: " + e.getMessage());
            return ResponseEntity.badRequest().body(response);

        } catch (Exception e) {
            LOG.error("Error processing config", e);
            response.put("status", "error");
            response.put("message", "Internal error: " + e.getMessage());
            return ResponseEntity.status(500).body(response);
        }
    }

    @GetMapping("/status/{jobId}")
    public ResponseEntity<Map<String, Object>> getJobStatus(
            @PathVariable String jobId) {

        JobStatus status = jobRegistryService.getJobStatus(jobId);

        if (status == null) {
            return ResponseEntity.notFound().build();
        }

        Map<String, Object> response = new HashMap<>();
        response.put("status", "success");
        response.put("jobId", status.getJobId());
        response.put("jobStatus", status.getStatus());
        response.put("submittedAt", status.getSubmittedAt());

        return ResponseEntity.ok(response);
    }

    @GetMapping("/health")
    public ResponseEntity<Map<String, Object>> health() {
        Map<String, Object> response = new HashMap<>();
        response.put("status", "UP");
        response.put("service", "etl-api");
        response.put("timestamp", Instant.now());
        return ResponseEntity.ok(response);
    }
}
```

6.2.3 ConfigService

```java
@Service
public class ConfigService {
    private static final Logger LOG =
        LoggerFactory.getLogger(ConfigService.class);

    @Value("${kafka.config.topic}")
    private String configTopic;

    private final KafkaTemplate<String, String> kafkaTemplate;
    private final ObjectMapper objectMapper;

    public void validateConfig(EtlConfig config) {
        if (config.getJobId() == null || config.getJobId().isEmpty()) {
            throw new IllegalArgumentException("jobId is required");
        }

        if (config.getSource() == null || config.getSource().isEmpty()) {
            throw new IllegalArgumentException("source is required");
        }

        if (config.getTransformations() != null) {
            for (Transformation t : config.getTransformations()) {
                validateTransformation(t);
            }
        }
    }

    private void validateTransformation(Transformation t) {
        if (t.getType() == null || t.getType().isEmpty()) {
            throw new IllegalArgumentException(
                "Transformation type is required");
        }

        // Validate aggregation transformations
        if (isAggregation(t.getType())) {
            if (t.getParams() == null ||
                !t.getParams().containsKey("field")) {
                throw new IllegalArgumentException(
                    "Aggregation requires 'field' parameter");
            }
        }

        // Validate filter transformations
        if (isFilter(t.getType())) {
            if (t.getParams() == null ||
                !t.getParams().containsKey("threshold")) {
                throw new IllegalArgumentException(
                    "Filter requires 'threshold' parameter");
            }
        }
    }

    public void publishConfig(EtlConfig config) throws Exception {
        String json = objectMapper.writeValueAsString(config);

        ProducerRecord<String, String> record =
            new ProducerRecord<>(configTopic, config.getJobId(), json);

        kafkaTemplate.send(record).get();  // Wait for confirmation

        LOG.info("Published config for job: {} to Kafka",
                config.getJobId());
    }
}
```

```java
@Service
public class FileProducerService {
    private static final Logger LOG =
        LoggerFactory.getLogger(FileProducerService.class);

    @Value("${producer.mode}")
    private String mode;  // "random" or "file"

    @Value("${producer.rate.per.sec}")
    private int ratePerSec;

    @Value("${kafka.input.topic}")
    private String inputTopic;

    private final KafkaTemplate<String, String> kafkaTemplate;
    private final ObjectMapper objectMapper;
    private final Random random = new Random();

    @Scheduled(fixedDelayString = "${producer.rate.ms}")
    public void produceData() {
        try {
            if ("random".equals(mode)) {
                produceRandomSensorData();
            } else if ("file".equals(mode)) {
                produceFromFile();
            }
        } catch (Exception e) {
            LOG.error("Error producing data", e);
        }
    }

    private void produceRandomSensorData() throws Exception {
        SensorEvent event = generateRandomEvent();
        String json = objectMapper.writeValueAsString(event);

        ProducerRecord<String, String> record =
            new ProducerRecord<>(inputTopic, event.getSensor(), json);

        kafkaTemplate.send(record);

        LOG.debug("Produced random event: sensor={}, measurement={}",
                 event.getSensor(), event.getMeasurement());
    }

    private SensorEvent generateRandomEvent() {
        String[] sensors = {
            "temperature_sensor_001",
            "temperature_sensor_002",
            "humidity_sensor_001",
            "pressure_sensor_001"
        };

        String sensor = sensors[random.nextInt(sensors.length)];

        SensorEvent event = new SensorEvent();
        event.setSensor(sensor);
        event.setMeasurement(generateRealisticValue(sensor));
        event.setMeasurementUnit(getUnitForSensor(sensor));
        event.setLocation("Room_" + (char)('A' + random.nextInt(5)));
        event.setDataQuality("high");
        event.setDatetime(Instant.now());

        return event;
    }

    private double generateRealisticValue(String sensor) {
        if (sensor.contains("temperature")) {
            // Realistic temperature range: 15-30°C
            return 15.0 + (random.nextDouble() * 15.0);
        } else if (sensor.contains("humidity")) {
            // Humidity: 30-90%
            return 30.0 + (random.nextDouble() * 60.0);
        } else if (sensor.contains("pressure")) {
            // Atmospheric pressure: 980-1030 hPa
            return 980.0 + (random.nextDouble() * 50.0);
        }
        return random.nextDouble() * 100.0;
    }

    private String getUnitForSensor(String sensor) {
        if (sensor.contains("temperature")) return "Celsius";
        if (sensor.contains("humidity")) return "Percent";
        if (sensor.contains("pressure")) return "hPa";
        return "Units";
    }
}
```
